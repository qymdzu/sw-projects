## 3. P1 问题清单（严重级）

> 共 **5 项**，建议在 Stage 7 测试执行期间同步加固，并进入回归测试。

### P1-01：JWT Secret 默认值存在弱密钥风险

| 项 | 内容 |
|:-----|:-----|
| 位置 | `backend/internal/config/config.go:76` |
| 严重程度 | P1（高）|
| 类型 | 配置安全 |

**问题描述**：
```go
Secret: getEnvStr("JWT_SECRET", "dev-secret-please-replace-in-production"),
```
当 `JWT_SECRET` 环境变量未设置时，默认值是固定的 `"dev-secret-please-replace-in-production"`。如果生产部署忘记设置 `JWT_SECRET`，将使用公开已知的默认密钥签发 JWT，攻击者可伪造任意用户身份。

**当前防御**：
- `config.go` 末尾有 `if cfg.JWT.Secret == "" { return nil, error }` 检查空值
- 但默认值非空，所以此检查对默认值无效

**修复建议**：
1. 在 `cfg.JWT.Secret` 等于默认值时，启动时输出 `WARN` 警告
2. 当 `APP_ENV=prod` 时，若 Secret 为默认值则 `Fatal` 拒绝启动
3. 进一步：使用 `crypto/rand` 至少 32 字节熵校验

**加固代码（示意）**：
```go
const defaultJWTSecret = "dev-secret-please-replace-in-production"
if cfg.JWT.Secret == defaultJWTSecret && cfg.Logger.Env == "prod" {
    log.Fatalf("JWT_SECRET must be explicitly set in production")
}
if cfg.JWT.Secret == defaultJWTSecret {
    logger.L().Warn("JWT_SECRET is using default value, please replace for production")
}
```

### P1-02：CORS 配置错误（Allow-Origin: \* + Allow-Credentials: true）

| 项 | 内容 |
|:-----|:-----|
| 位置 | `backend/internal/middleware/cors.go:5-21` |
| 严重程度 | P1（中）|
| 类型 | 安全配置 |

**问题描述**：
```go
c.Writer.Header().Set("Access-Control-Allow-Origin", "*")
c.Writer.Header().Set("Access-Control-Allow-Credentials", "true")
```
根据 CORS 规范，浏览器会**拒绝**这种组合（`Allow-Origin: *` 与 `Allow-Credentials: true` 不能共存）。当前应用使用 `Authorization: Bearer` Token 鉴权，不依赖 Cookie，所以业务上暂未受影响，但配置错误会导致：
1. 未来若切换到 Cookie 鉴权将产生隐性安全风险
2. 跨域携带凭据的请求会被拒绝（潜在功能缺陷）

**修复建议**：
1. 根据配置文件中的可信 Origin 列表动态设置 `Access-Control-Allow-Origin`
2. 简单方案：MVP 阶段先去掉 `Allow-Credentials: true`（因为不依赖 Cookie）

**加固代码（示意）**：
```go
func CORS(allowedOrigins []string) gin.HandlerFunc {
    return func(c *gin.Context) {
        origin := c.GetHeader("Origin")
        if origin != "" && contains(allowedOrigins, origin) {
            c.Writer.Header().Set("Access-Control-Allow-Origin", origin)
            c.Writer.Header().Set("Vary", "Origin")
            c.Writer.Header().Set("Access-Control-Allow-Credentials", "true")
        }
        // ... 其余头
    }
}
```

### P1-03：ServerError 直接返回底层错误信息（信息泄露）

| 项 | 内容 |
|:-----|:-----|
| 位置 | `internal/handler/*.go` 多处 |
| 严重程度 | P1（高）|
| 类型 | 信息泄露 |

**问题描述**：
```go
// 例：internal/handler/exercise_handler.go:118
items, total, err := h.svc.List(c.Request.Context(), filter)
if err != nil {
    response.ServerError(c, err.Error())  // ← 把数据库错误直接返回给客户端
    return
}
```
类似的错误处理在以下位置出现：
- `exercise_handler.go`：List / Random / Recommend / ByKnowledgePoint / History
- `mistake_handler.go`：List / Groups / Review / MarkMastered / Delete
- `plan_handler.go`：List（错误用 ServerError，其余错误用 BadRequest）
- `report_handler.go`：Summary / Detail / Mastery / Trend

底层错误（特别是数据库错误）可能包含 SQL 语句片段、表名、字段约束等敏感信息，攻击者可借此推断数据库结构。

**修复建议**：
1. Handler 层对底层错误统一包装为通用错误（如"服务暂时不可用"）
2. 详细错误（含 stack trace）记录到日志

**加固模式（示意）**：
```go
items, total, err := h.svc.List(c.Request.Context(), filter)
if err != nil {
    logger.L().Error("list exercises failed", "err", err.Error(), "user_id", uid)
    response.ServerError(c, "查询失败，请稍后重试")
    return
}
```

### P1-04：Register 唯一性校验吞掉数据库错误

| 项 | 内容 |
|:-----|:-----|
| 位置 | `internal/service/auth_service.go:104-113` |
| 严重程度 | P1（中）|
| 类型 | 错误处理不完整 |

**问题描述**：
```go
if req.Phone != "" {
    if existing, _ := s.users.GetByPhone(ctx, req.Phone); existing != nil {
        return nil, ErrAccountConflict
    }
}
if req.Email != "" {
    if existing, _ := s.users.GetByEmail(ctx, req.Email); existing != nil {
        return nil, ErrAccountConflict
    }
}
```
此处 `GetByPhone/GetByEmail` 的错误被忽略（`_` 丢弃）。如果数据库连接中断或查询超时，应用层会把"系统错误"误判为"账号不存在"，最终走到 `Create` 时再失败（因唯一索引）或异常写入。

**修复建议**：
```go
if req.Phone != "" {
    existing, err := s.users.GetByPhone(ctx, req.Phone)
    if err != nil && !errors.Is(err, repository.ErrNotFound) {
        return nil, fmt.Errorf("查询用户失败: %w", err)
    }
    if existing != nil {
        return nil, ErrAccountConflict
    }
}
```

## 5. 关键业务逻辑审查记录

### 5.1 注册流程（DoD-01）

```
注册请求 → 字段校验（非空、手机/邮箱格式、密码强度）
  → 唯一性校验（应用层查询 + DB 唯一索引双保险）
  → bcrypt(cost=10) 密码哈希
  → UUID 主键生成（uuid.New）
  → 写入 users 表
  → 颁发 access + refresh 双 Token
  → 返回脱敏后的用户信息 + Token
```

✅ **结论**：符合 DoD-01，逻辑闭环。**注意**：唯一性校验的错误处理见 P1-04。

### 5.2 登录流程（DoD-01）

```
登录请求 → 字段校验
  → 识别账号类型（手机号/邮箱，走 validator）
  → 查 users 表
  → bcrypt 校验密码（常时实现）
  → 颁发双 Token
  → 返回脱敏后的用户信息 + Token
```

✅ **结论**：符合 DoD-01。
- 用户枚举防护：账号不存在/密码错误统一返回 `"账号或密码错误"`
- 防时序攻击：bcrypt 校验失败与成功耗时相近

### 5.3 练习批改（DoD-04）

```
提交答案 → 校验 question_id 和 answer 非空
  → 取题目（包含 correct answer）
  → judgeAnswer:
      choice/judge: EqualFold（容忍大小写）
      fill:        "|" 分隔多答案，任一匹配即正确
      subjective:  宽松匹配（user_answer 包含 correct 关键词即视为正确）
      default:     false
  → 写入 exercise_records 表
  → 错误时调用 recordMistakeHelper：
      查错题本，已存在 → IncrementCount（原子）
             不存在 → Create 新记录
  → 返回批改结果（含正确答案、解析、是否收录错题）
```

✅ **结论**：符合 DoD-04（实时反馈）。
- 主观题宽松匹配是 MVP 妥协，文档中应标注
- 错题收录幂等性 ✓

### 5.4 错题收录（DoD-05）

```
答错 → recordMistakeHelper:
       GetByUserQuestion → 已存在 → IncrementCount（gorm.Expr 原子）
                       → 不存在 → Create（mistake_count=1, mastered=false）
```

✅ **结论**：符合 DoD-05。

### 5.5 学习计划与打卡（DoD-02、DoD-03）

```
创建计划 → 校验 goal/start_date/end_date
       → JSON 序列化 items
       → 写入 study_plans

AI 生成 → 规则降级（按 start_date~end_date 每天生成 item）
       → 返回 ai_used=false（MVP 实际未调用 LLM）

打卡 → 校验计划存在且属于当前用户
     → 写入 study_records
```

✅ **结论**：符合 DoD-02、DoD-03。AI 限制见 P1-05。

### 5.6 学习报告（DoD-07）

```
Summary → 聚合今日/总学习时长、练习数、正确率、连续打卡、未掌握错题
Detail  → 按 period_type 聚合 + 按日拆分（最多 60 天）
Mastery → 按 subject_id 聚合知识点掌握度（rate ≥ 0.85 mastered）
Trend   → 按天聚合（默认 7 天，最多 60 天）
```

✅ **结论**：符合 DoD-07。`s.reports` 字段为 V1.5 异步报告预留。

## 6. 安全审查明细

### 6.1 SQL 注入

**审查范围**：所有 `r.db.WithContext(ctx).Where(...)` 调用

✅ **结论**：全部使用 `?` 占位符 + 参数绑定，无字符串拼接风险。

### 6.2 XSS

**审查范围**：响应输出

✅ **结论**：所有响应为 JSON，由前端负责 HTML 转义。`name/email/memo/analysis` 字段虽含用户输入，但经过 JSON 序列化（`json:"-"` / `json:"..."`），由前端模板层负责转义。

### 6.3 CSRF

**审查范围**：Cookie / Session / 表单提交

✅ **结论**：纯 Bearer Token 鉴权，不依赖 Cookie / Session，因此**不存在传统 CSRF 风险**。这是架构设计的优势。

### 6.4 JWT 安全

| 检查 | 结果 |
|:-----|:-----|
