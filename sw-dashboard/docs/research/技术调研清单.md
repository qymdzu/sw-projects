## 维度 1：FastAPI 项目结构最佳实践 ✅

### 方案对比

| 方案 | 描述 | 适用场景 | 推荐 |
|:-----|:-----|:---------|:-----|
| **A. 扁平结构** | router/service/model 各一个文件 | 极简项目（<5 路由） | ❌ |
| **B. 模块化分层 (推荐)** | routers/services/models 按功能域拆分目录 | 中型项目，功能模块清晰 | ⭐⭐⭐ |
| **C. 领域驱动 (DDD)** | 按业务领域分包（dashboard/storage/logs） | 大型多人协作项目 | 过度设计 |

### 推荐方案 B 理由

1. **关注点分离**：路由（HTTP 层）⇢ 服务（业务层）⇢ 模型（数据层）
2. **渐进式复杂度**：从单文件起步，随需求增加自然拆分
3. **FastAPI 官方推荐**：与 FastAPI 官方示例和 cookie-cutter 模板一致
4. **测试友好**：依赖注入使单元测试可以 mock 服务层

### 关键模式

- `APIRouter` 前缀路由挂载
- `Depends()` 注入认证/路径依赖
- Pydantic v2 `BaseModel` 定义请求/响应 Schema
- `BackgroundTasks` 处理备份等非关键操作

## 维度 3：文件系统浏览方案 ✅

### Python 标准库方案对比

| 方案 | 实现 | 优点 | 缺点 | 推荐 |
|:-----|:-----|:-----|:-----|:-----|
| **A. pathlib (推荐)** | `Path.iterdir()` + 递归 | 现代 API，跨平台，零依赖 | 大目录首次加载慢 | ⭐⭐⭐ |
| **B. os.listdir + os.path** | 传统方案 | 兼容性好，Python 2/3 都支持 | API 过时，返回纯字符串 | ❌ |
| **C. scandir + DFS** | `os.scandir()` 迭代 | 不会一次性加载整个目录 | 编码略复杂 | ⭐⭐ |
| **D. watchdog (第三方)** | 文件系统事件监听 | 可实时监测文件变化 | 需要额外依赖，复杂度过高 | ❌ |

### 推荐方案 A (pathlib) 理由

- `Path` 对象天然支持 `/` 拼接、`.suffix`、`.stem` 等属性
- Python 3.4+ 标准库，无需安装额外包
- 搭配 `sorted(iterdir(), key=...)` 可控制排序（目录优先）
- 排除规则：`entry.name.startswith('.')` 过滤隐藏文件
- 懒加载优化：`<el-tree>` 的 `lazy` 模式 + `load` 函数按需加载子节点

### 方案 A 的实现要点

```python
from pathlib import Path

def build_tree(root: Path, max_depth: int = 5) -> list[dict]:
    """递归生成目录树，带深度限制防栈溢出"""
    if max_depth <= 0:
        return []
    items = []
    for entry in sorted(root.iterdir(), key=lambda e: (not e.is_dir(), e.name.lower())):
        if entry.name.startswith('.'):
            continue
        node = {"label": entry.name, "path": str(entry), "isLeaf": not entry.is_dir()}
        if entry.is_dir():
            node["children"] = build_tree(entry, max_depth - 1)
        items.append(node)
    return items
```

## 维度 4：日志 tail/轮询方案 ✅

### 方案对比矩阵

| 特性 | REST 轮询 (推荐) | WebSocket | SSE |
|:-----|:-----------------|:----------|:----|
| **实现复杂度** | 极低（现有 API 即可） | 高（需 ws 库 + 连接池管理） | 中 |
| **前端代码** | 3 行 setInterval | 需 ws 事件处理 + 重连逻辑 | EventSource API |
| **后端依赖** | 无额外 | `websockets` + `fastapi-websocket` | 无额外 |
| **实时性** | 3s 延迟（内网可接受） | 毫秒级 | 秒级 |
| **连接开销** | 无持久连接 | 每个客户端一个 ws 连接 | 每个客户端一条 HTTP 长连接 |
| **资源占用** | 极低 | 中（旧云服务器需谨慎） | 中 |
| **浏览器兼容** | 全兼容 | 全兼容 | 不支持 IE |
| **调试友好度** | 直接 curl 测试 | 需 ws 客户端 | 有限 |

### 推荐 REST 轮询理由

1. **需求明确"定时轮询刷新"** — 这是已确定的决策
2. 旧云服务器资源有限，WebSocket 长连接对 512MB 内存不友好
3. 3 秒轮询间隔对内网场景完全可接受
4. 实现最简单，后端无需改动架构

### Python 日志 tail 核心算法

```python
def tail_file(filepath: Path, n: int = 100) -> str:
    """从文件尾反向读取 N 行，性能优化版"""
    CHUNK_SIZE = 4096
    with open(filepath, 'rb') as f:
        f.seek(0, os.SEEK_END)
        file_size = f.tell()
        if file_size == 0:
            return ""
        
        buffer = []
        chunks_read = 0
        while len(buffer) < n and chunks_read * CHUNK_SIZE < file_size:
            start = max(0, file_size - (chunks_read + 1) * CHUNK_SIZE)
            chunk_size = min(CHUNK_SIZE, file_size - start)
            f.seek(start)
            chunk = f.read(chunk_size)
            buffer.insert(0, chunk)
            chunks_read += 1
        
        content = b''.join(buffer)
        lines = content.decode('utf-8', errors='replace').splitlines()
        return '\n'.join(lines[-n:])
```

## 维度 5：内网部署方案 ✅

### Tailscale + systemd 方案对比

| 方案 | 说明 | 优点 | 缺点 | 推荐 |
|:-----|:-----|:-----|:-----|:-----|
| **A. systemd 原生 (推荐)** | 直接管理 uvicorn 进程 | 零依赖，流程简单 | 无负载均衡 | ⭐⭐⭐ |
| **B. Docker + systemd** | 容器化部署 | 环境隔离 | 额外资源开销，旧云服务器安装 Docker 麻烦 | ❌ |
| **C. supervisor** | Python 进程管理 | 配置灵活 | 额外学习成本 | ⭐ |
| **D. tmux/screen** | 手动启动 | 极简 | 需要 SSH 连接，重启后丢失 | ❌ |

### 推荐方案 A 理由

1. systemd 是 Linux 标准，无需额外安装
2. `Restart=always` 保证服务崩溃后自动恢复
3. Tailscale 网络已接入，防火墙规则只需允许 Tailscale 网段
4. 单进程部署（`--workers 1`）即可满足需求

### 网络安全拓扑

```
[公子的 ThinkPad]
    │
    ├── Tailscale 100.x.x.x:8900 ──── [旧云服务器]
    │                                  │
    │                                  ├── systemd → sw-dashboard.service
    │                                  │       └── uvicorn main:app --host 0.0.0.0:8900
    │                                  │
    │                                  ├── iptables: 仅允许 100.64.0.0/10 访问 8900
    │                                  │
    │                                  └── HTTP 请求

    │                                          └── /* → Vue SPA (静态文件托管)
    │
    └── 飞书（可选）— 日常沟通渠道，与控制面板解耦
```

## 维度 6：前端后端通信方式 ✅

### API 通信方案对比

| 方案 | 说明 | 优点 | 缺点 | 推荐 |
|:-----|:-----|:-----|:-----|:-----|
| **A. REST + axios (推荐)** | 标准 HTTP + JSON | 简单直观，调试方便 | 无实时推送 | ⭐⭐⭐ |
| **B. tRPC** | TypeScript 类型安全 RPC | 类型推导好 | 需要全栈 TS，Python 生态差 | ❌ |
| **C. GraphQL** | 按需查询 | 灵活查询 | 过度设计，学习成本高 | ❌ |
| **D. WebSocket 全双工** | 一个连接所有通信 | 实时双向 | 复杂，不适合 CRUD 场景 | ❌ |

### 推荐方案 A 理由

1. REST 是 Web 最成熟的通信协议，工具链完备
2. axios 拦截器可统一处理 Token 注入、错误提示、加载态
3. FastAPI 自动生成 OpenAPI 文档，方便调试
4. 所有操作都是"请求-响应"模式，REST 天然适合

### axios 实例封装

```typescript
// src/api/index.ts
import axios from 'axios'
import { ElMessage } from 'element-plus'

const api = axios.create({
  baseURL: '/api',
  timeout: 10000,
  headers: { 'Content-Type': 'application/json' }
})

// 请求拦截器：注入 Token
api.interceptors.request.use(config => {
  const token = localStorage.getItem('dashboard_token')
  if (token) config.headers['X-Token'] = token
  return config
})

// 响应拦截器：统一错误处理
api.interceptors.response.use(
  response => response,
  error => {
    const msg = error.response?.data?.detail || error.message
    ElMessage.error(msg)
    return Promise.reject(error)
  }
)

export default api
```

    ↓ (axios GET/POST)

    ↓ (Depends 验证)

### 推荐：CodeMirror 6

**核心理由**：
1. **轻量匹配定位**：翠花面板是"配置编辑"而非"代码编写"，不需要完整的 IDE 能力
2. **vue-codemirror 开箱即用**：Vue 3 Composition API 友好封装，直接 `<codemirror>` 组件
3. **语言包按需加载**：仅安装需要的语言包，生产包更小
4. **旧云服务器友好**：包体积小，加载快，适合低配机器

### CodeMirror 6 的 Vue 集成示例

```vue
<template>
  <div class="editor-wrapper">
    <codemirror
      v-model:value="content"
      :extensions="extensions"
      :disabled="readonly"
      :style="{ height: '500px' }"
      @ready="handleReady"
    />
  </div>
</template>

<script setup lang="ts">
import { ref, computed } from 'vue'
import { Codemirror } from 'vue-codemirror'
import { oneDark } from '@codemirror/theme-one-dark'
import { yaml as yamlLang } from '@codemirror/lang-yaml'
import { markdown as mdLang } from '@codemirror/lang-markdown'
import { python as pyLang } from '@codemirror/lang-python'

const props = defineProps<{
  language: 'yaml' | 'markdown' | 'python' | 'env'
  readonly?: boolean
  content: string
}>()

const emit = defineEmits<{
  'update:content': [value: string]
}>()

const localContent = ref(props.content)

const extensions = computed(() => {
  const langMap: Record<string, any> = {
    yaml: yamlLang(),
    markdown: mdLang(),
    python: pyLang(),
    env: yamlLang(), // .env 也使用 yaml 高亮
  }
  return [oneDark, langMap[props.language] || yamlLang()]
})

function handleReady(view: any) {
  console.log('Editor ready', view)
}
</script>
```

### 备选方案：何时使用 Monaco Editor

- 需要编辑大规模代码文件（> 1000 行）
- 需要 VS Code 级别的智能感知和代码补全
- 服务器内存充裕（> 2GB）
- 用户对编辑体验有 IDE 级别的期望

当前翠花面板不满足上述任一条件，故选择 CodeMirror 6。
